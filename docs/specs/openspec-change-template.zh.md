# OpenSpec 变更内置模板

## 范围与行为

- 默认 bundle 通过独立模板包和通用加载器提供中文模板 `openspec-change.zh`，展示名称为“OpenSpec 变更工作流”。
- 顺序为填写需求 → 澄清需求与生成方案 → 实施与验证 → 同步规格与归档。默认使用实例工作区，一个实例对应一个 change。
- 入口表单产生原始 `request`。方案会话调用 `openspec-propose`，澄清需求、在创建 change 前确定名称并生成规划产物；不另设起名会话和名称确认表单。
- 方案节点声明输出 `change_name: string`。用户审阅方案并点击完成后，使用已有 Agent 结构化交付机制提取实际创建的名称；提取失败不推进下游，可补充原会话后重试。
- 名称从方案节点直接传给实施与归档。原始需求保留在入口供追溯，后续独立会话从磁盘读取实际规划产物与已澄清决策，不重复接收原始需求。实施与归档完成仅提交 `{}`。
- 实施调用 `openspec-apply-change`，执行任务、验证并报告通过、失败和未验证项；规划变化在当前会话更新同一个 change 并取得必要决定后继续。归档调用 `openspec-archive-change`，完成状态检查、规格同步选择与归档。
- 所有会话手动启动并由用户标记完成。方案阶段展示范围、关键决策、任务清单及产物位置；实施展示完成内容、验证结果及剩余问题；归档展示同步结果、归档位置及警告。
- 模板不安装 OpenSpec 或 dsh、不自动初始化项目，不改造现有节点能力，也不增加 store 选择、改名流程或额外审批表单。技能缺失、阻塞、失败或取消留在对应会话处理。

## 验收场景

1. 默认 bundle 可加载并创建模板实例，四个中文节点通过 DAG 和实际节点配置校验。
2. 提交需求后方案节点收到完整 `request`，保留中文、引号与换行；没有独立起名节点或名称表单。
3. 方案节点声明结构化输出；会话回复后实施仍等待，只有用户完成方案并成功交付 `change_name` 后实施才就绪。
4. 实施与归档只收到相同的 `change_name`，均不自动启动；归档还须等待实施完成，不从实施的空输出取名称。
5. 方案交付后重启真实宿主，保留名称和阶段状态，实施与归档仍使用同一个 change 名称。完成归档后 DAG 完成。
6. 确定性模型夹具仅验证宿主交接机制；实际 OpenSpec 技能执行与真实模型产物质量单独标记验证范围。
