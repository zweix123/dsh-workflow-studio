# 节点与 DAG 的运行记录

状态：已实施（2026-10-15）；自动化及真实宿主验证范围、当前结论与未验证项见[验收记录](../acceptance/node-run-records.zh.md)。测试接口已由用户确认。项目尚未提供 Issue tracker 与 triage 配置，本次以本地规格实施，未发布 Issue，也未应用 ready-for-agent 标签。

## Problem Statement

工作流使用者需要查看节点发生了什么异常、已经重试几次，以及每次尝试使用的输入和产生的结果。当前各类型的查看方式不一致：Bash 主要保留最近一次执行事实，Agent 自行保存历次子执行并提供记录选择，Form 展示已接受结果和交付错误。重试后旧日志或结果可能无法追溯，使用者难以判断本次操作是否重复执行业务。

节点业务失败和结果交付 DAG 失败又是两种不同情况。当前 Bash 的“执行”、Agent 的“完成”在已有成功结果时会只重交结果，相同按钮文案却也承担实际业务操作，使用者无法仅凭按钮判断是否会再次运行命令或调用 Agent。业务已经成功但编排尚未完成时，也需要准确表达两种事实。

普通节点与 DAG 已有各自的详情入口，不同层级的异常面向不同的处理人员。把所有错误放进普通节点、嵌套展示业务与编排历史，或增加两边的关联跳转，都不符合本次需求。使用者需要的是在各自详情中采用一致的位置和格式，查看由该对象负责的内容。

## Solution

在现有详情抽屉中增加统一位置与格式的只读运行记录区域。普通节点展示自己的历次业务尝试，DAG 展示自身的编排异常及后续重试、恢复情况；不建设工作流实例级汇总入口，不新增占用金刚位，也不增加普通节点与 DAG 历史之间的关联展示或跳转。

记录最近一次在前，默认展开最新一次。每条摘要提供次数、操作名称、状态、开始时间及失败摘要；展开后查看当次输入、结果、完整错误和各类型专属内容。Bash 提供实际命令与日志，Agent 提供实际提示词和对应原生执行记录入口，Form 提供正式提交值，DAG 提供编排错误位置和详情。各节点管理自身记录内容，公共区域提供统一外壳。

Agent 金刚位的“记录”直接进入最新一次尝试的原生执行记录。最新尝试没有地址时，入口禁用并说明原因；旧记录从详情中的历史访问。所有业务动作继续由节点在金刚位按状态定义：Bash 首次显示“执行”，失败或结果未知后显示“重新执行”，任何节点重交已接受结果时统一显示“重试交付”。

业务成功结果已接受、但 DAG 交付失败时，业务历史仍显示“成功”，节点当前状态显示“业务完成，交付失败”，具体编排异常在相应 DAG 详情展示。只有 DAG 推进及新图状态保存都成功，节点才显示“已完成”。

运行历史随工作流实例保存，重启后仍可查看，删除实例时一起删除。没有确定结果的中断尝试恢复为结果未知，不自动重跑；已保存的待确认结果仍等待确认，已接受的成功结果仅重交 DAG。开始记录保存失败则不启动业务，最终结果保存失败不能宣称结果已接受。不建设旧实例兼容、迁移或历史补齐方案。

## User Stories

1. 作为工作流使用者，我希望在现有详情抽屉查看运行记录，以便沿用已有的检查路径。
2. 作为工作流使用者，我希望不同节点类型的记录位于相同区域并采用一致格式，以便不必学习多套查看方式。
3. 作为工作流使用者，我希望查看历史不占用额外金刚位，以便保留节点的业务操作入口。
4. 作为工作流使用者，我希望普通节点只展示自己的业务尝试，以便专注处理该节点的问题。
5. 作为编排维护者，我希望在相应 DAG 的详情查看编排异常，以便在负责的层级排查问题。
6. 作为编排维护者，我希望嵌套 DAG 与祖先 DAG 的错误按实际归属展示，以便不会把祖先错误误判为直接父 DAG 的错误。
7. 作为工作流使用者，我希望普通节点与 DAG 的历史独立展示，以便不同处理人员各自查看负责的内容。
8. 作为工作流使用者，我希望每次实际业务尝试都被保留，以便重试不会覆盖此前的情况。
9. 作为工作流使用者，我希望历史包含成功、失败和结果未知，以便能够理解完整的尝试过程。
10. 作为工作流使用者，我希望最近一次记录排在最前，以便快速查看当前问题。
11. 作为工作流使用者，我希望默认展开最新一次、折叠此前记录，以便历史较多时仍易于阅读。
12. 作为工作流使用者，我希望展开旧记录时能够查看当次内容，以便比较不同尝试的差异。
13. 作为工作流使用者，我希望摘要显示次数和操作名称，以便区分具体发生了哪种处理。
14. 作为工作流使用者，我希望摘要显示开始时间和状态，以便判断尝试的先后与进展。
15. 作为工作流使用者，我希望失败摘要和完整错误都可查看，以便兼顾快速判断与详细排查。
16. 作为工作流使用者，我希望每次尝试保留实际输入，以便知道当时处理了什么数据。
17. 作为工作流使用者，我希望每次尝试保留自己的结果，以便成功后的重试不会使旧结果消失。
18. 作为 Bash 使用者，我希望查看当次实际使用的命令，以便无需根据当前模板猜测过去执行了什么。

23. 作为 Bash 使用者，我希望失败或结果未知后的按钮显示“重新执行”，以便清楚点击会再次产生业务执行。

## Implementation Decisions

- **职责与接入。** 沿用独立节点公共契约、profile 级登记和 Studio 执行协调。节点解释自身业务状态、记录内容及专属展示，Studio 统一协调持久化、业务结果接受和 DAG 推进。通用外壳不识别各类型私有业务字段。节点插件不得依赖 Studio 的工作流、DAG 或工作流实例状态类型；DAG 编排记录由现有编排协调提供。
- **修改范围。** 修改公共节点服务端及浏览器展示契约、工作流执行与持久化协调、实例查询与响应校验、详情抽屉公共运行区域、各内置节点的记录与动作描述，以及宿主语言词表。复用已有登记、查询和动作分派入口，不为运行历史另建调度系统或测试专用产品接口。具体类型名称和存储布局在实施时按实际需求确定。
- **实例归属。** 每个普通节点实例管理自己的业务历史，每个 DAG 实例管理自己的编排历史；不得按定义标识把逐项展开、嵌套或递归产生的不同实例混在一起。普通节点与 DAG 的记录保持独立，不增加两边的关联列表、互相跳转或重复错误详情，也不采用业务尝试内嵌 DAG 提交历史的展示。
- **业务记录边界。** 每次实际业务尝试形成独立记录，新尝试不覆盖旧记录；同次尝试的进行中信息和最终结果属于该次记录。Bash 命令执行、Agent 台后任务与台前结果提取、Form 正式提交均在其实际处理边界记录。普通填写校验、只读查看和因运行中等原因被拒绝的重复操作不构成业务尝试。仅重交确定结果不制造新的业务执行记录。
- **DAG 记录边界。** 记录编排异常以及此后的重试、恢复结果，不扩充为所有正常推进事件的过程追踪。保留足够的错误阶段、代码和位置信息，使边表达式、合并、展开、聚合、输入契约及 DAG 输出错误能够按实际责任归属展示。一次叶子提交可能失败在祖先 DAG，下游实例可能尚未创建，不得仅用触发节点的直接父 DAG 或假定存在的下游实例定位。定位信息服务于本层诊断，不要求增加用户可见的跨层关联。
- **记录快照。** 每次业务尝试保存实际输入、当次使用的命令或提示词、结果和错误，并保留自身标识、顺序、操作名称、状态和时间。快照必须对应该次实际使用的内容，不能在查看历史时用当前模板、当前文件或重新渲染的文本替代。Form 提交值属于当次记录；Bash 日志与合法业务输出分别呈现。工作区文件不复制，原生 Agent 详细过程仍由宿主记录提供。
- **错误内容与状态。** 业务执行或结果校验错误放普通节点，编排处理错误放对应 DAG；按可取得的结构化信息展示阶段、错误代码、摘要和完整诊断。业务尝试可以处于进行中、成功、失败或结果未知，不以当前节点的一份错误覆盖全部历史。正常待确认结果与失败、未知分别表达。
- **统一详情。** 在现有详情抽屉使用统一位置及摘要格式，最近一次在前、最新一次默认展开、其他记录默认折叠。摘要包括次数、操作名称、状态、开始时间及失败摘要。各类型提供展开后的内容：Bash 命令与日志、Agent 提示词和原生地址、Form 提交值、DAG 编排诊断。复用宿主组件与主题变量，适配中英文、浅深主题、窄屏和键盘。详情不获得业务执行、确认或重用旧结果的能力；允许查看、复制和原生记录导航。
- **Agent 导航。** 金刚位“记录”严格指向最新一次尝试的原生执行记录，取消多次记录选择浮窗。最新尝试尚未生成地址或创建失败没有地址时，入口禁用并提供可理解的原因，不回退打开较早记录。旧记录通过历史访问；历史中的无地址项仍可查看状态和错误，但不得提供无效导航。台前主对话仍使用独立的对话动作。
- **金刚位动作。** 节点按当前状态自由定义现有操作位的动作。Bash 首次业务运行显示“执行”，失败或未知后显示“重新执行”；台前 Agent 的“完成”仍负责业务完成及必要的结果提取，台后 Agent 仍区分任务重试与人工确认。任意节点已有接受结果但 DAG 交付失败时统一显示“重试交付”，不能再让“执行”或“完成”暗含这一分支。是否复用内部动作身份由实现决定，服务端始终按真实状态校验，不依赖文案保证行为。
- **成功与交付。** 先验证并可靠保存接受的业务结果，再协调 DAG 提交。业务成功但提交异常时，该次业务历史保持成功，节点当前显示“业务完成，交付失败”，金刚位提供“重试交付”，具体编排错误在 DAG 详情。仅当 DAG 推进与新图状态保存均成功，节点才显示已完成。已接受结果不开放编辑或被后续请求覆盖；再次交付只使用保存结果，不重复命令、Agent 执行或结果提取。
- **现有恢复机制。** 沿用宿主启动及节点登记恢复时重交已保存成功结果的路径，不建立定时重交循环。临时存储故障恢复后可能交付成功，固定定义与结果导致的确定性编排错误可能持续失败；不将“重试交付”表达为保证恢复，也不新增热修复实例定义或修改确定结果的能力。
- **中断恢复。** 没有确定结果的中断业务执行或提取尝试恢复为结果未知，保留已保存的日志和原生地址。未经明确重新执行，不启动新业务。已保存的台后待确认结果仍等待人工确认；已接受的成功结果只恢复交付。历史必须与最后可靠保存的事实一致，不能根据页面曾显示过的内容猜测成功。
- **保存失败。** 开始记录未可靠保存时不得启动业务。业务执行后最终结果保存失败，不报告结果已接受、不推进 DAG，保留最后可靠事实，恢复按未知处理。错误记录本身也可能因同一存储故障无法保存，当前界面应反馈可获知的错误，不承诺重启后一定有完整诊断。异步执行和进度保存失败也遵守该原则，不另建后台保存重试系统。
- **并发与生命周期。** 沿用已有串行状态写入、同一节点在途操作保护、不同独立节点并行及卸载协调，防止重复点击、自动与手动启动重叠制造重复副作用或混淆记录。运行历史不能在其他分支完成或恢复时被旧状态覆盖；运行中删除保护与已保存事实的处理继续遵循现有规则。
- **保留与旧数据。** 历史随工作流实例持久保存并随实例删除，保留全部实际尝试次数。命令日志沿用宿主已有截断限制，发生截断时明确标识，不恢复宿主未提供的内容。不建设旧格式实例兼容、迁移或历史补齐，也不据此删除现有实例。删除实例历史不改变宿主原生会话既有的独立生命周期。
- **文档同步。** 实施时同步节点操作位规则、只读详情中的原生导航范围、三个内置节点说明、节点作者指南、语言文案及阅读导航。保留现有业务完成、确定结果、DAG 原子回滚和独立节点契约的职责约定；明确更新与本规格不同的多记录选择及动作文案规则，不能让当前与目标行为混为一谈。

## Testing Decisions

测试接口已由用户确认：以现有隔离真实 dsh 宿主的浏览器 UI 为主要验收接口，复用现有工作流实例 HTTP 接口补充持久化故障、并发和恢复测试；不新增测试专用产品接口。

好的测试验证用户可观察的状态、可访问历史、原始输入和结果、可用动作及实际副作用次数。不得仅镜像内部数组结构、私有函数或某份类型声明；也不得只证明按钮改名而未证明其实际行为。优先通过已有最高层接口覆盖完整链路，只有真实 UI 难以稳定控制的故障才使用既有宿主服务替身和存储故障夹具，通过公开查询和操作验证结果。

- **主要模块与先例。** 验收覆盖详情公共记录外壳、Bash／Agent／Form 节点插件、DAG 编排协调、实例查询与持久化恢复。复用已有真实宿主 Bash、Agent 交付、节点操作位、节点详情和 DAG 用例，以及工作流实例 HTTP 集成测试中的在途服务替身、存储重开和真实写入失败夹具。仅在现有公开契约需要补充时增加针对性的节点契约测试，不另建一套执行框架。
- **可重复浏览器用例。** 沿用项目隔离宿主夹具，每条用例独立准备模板、工作区与前置数据，通过 UI 完成被测操作并断言历史内容、状态、按钮及导航。接口只辅助准备或定位，不能替代被测 UI 动作。默认无界面、不录屏、不主动截图，不使用演示性固定等待；失败诊断遵循既有框架。
- **业务与交付副作用。** 利用文件内容、命令执行次数或确定性模型服务调用数证明“重新执行”确实新增业务尝试，“重试交付”不新增命令、Agent 任务或提取调用。通过实际故障恢复使同一结果最终交付成功，并另测确定性编排错误持续失败；不能只用永远失败的样例证明成功恢复。
- **持久化与故障。** 通过公开实例操作控制开始记录、业务结果和 DAG 图状态三个保存阶段，验证各自故障后的状态、历史和调用次数。沿用已有存储域故障注入及重开夹具，不为故障增加产品控制接口。命令已经执行但结果无法保存时，未知状态与不自动重跑必须有实际断言。
- **身份与并发。** 覆盖同定义在不同实例、逐项展开、嵌套与递归中的历史隔离；验证祖先 DAG 报错和尚未创建的下游位置能够正确归属。用可控未结束调用验证同节点重复操作被拒绝且不制造记录，不同分支并行完成后历史不丢失。
- **Agent 宿主能力。** 复用确定性模型边界夹具验证原生执行、结构化结果、记录地址和重启可读性；模型边界确定性不等于验证真实模型对任务语义或任意长上下文的判断质量。既有原生记录展示继续由宿主负责。

验收场景及预期如下；实际通过、失败与未验证状态统一见验收记录。

| 场景 | 预期 |
| --- | --- |
| Bash 连续失败后成功 | 各次实际输入、命令、stdout、stderr、退出情况、结果与错误均可查看，新尝试不覆盖旧记录；最新一次默认展开 |
| Bash 首次、失败与未知后的动作 | 首次显示执行，失败或未知后显示重新执行；点击实际增加一次业务调用与对应记录 |
| 日志截断 | 当次历史明确标识截断，部分日志不会被宣称为完整日志，其他次数和结果保留 |
| 台前 Agent 提取失败后再次完成 | 原对话继续可用，新的提取形成独立尝试，各次结果与错误保留，原生记录分别可访问 |
| 台后 Agent 失败后重新执行 | 失败不自动循环重试，新执行形成新记录；成功后保存待确认结果，确认不重新执行任务 |
| Agent 金刚位记录直达 | 多次尝试时也直接进入最新一次的原生记录，历史记录从抽屉分别打开，不再出现旧选择浮窗 |
| 最新 Agent 尝试尚无地址或创建失败 | 金刚位入口禁用并说明原因，不误开旧记录；历史中旧地址仍可查看，无地址项没有无效导航 |
| Form 正式提交与即时校验 | 正式处理的提交保留对应值与结果或拒绝信息；填写即时校验不产生历史；已接受结果只读 |
| 详情只读 | 能展开、复制与查看对应原生记录，无执行业务、重试、完成确认或重用旧结果动作 |
| 业务成功后编排失败 | 业务历史显示成功，节点当前显示业务完成、交付失败；编排错误在实际所属 DAG，普通节点不重复展示完整编排诊断 |
| 临时故障后重试交付成功 | 各类型统一显示重试交付；使用原结果，副作用调用次数不增加，可靠保存 DAG 状态后变为已完成 |
| 确定性编排错误持续失败 | 重交失败保持当前失败状态与历史，不重新收集结果、不修改模板快照，不声称必然恢复 |
| DAG 异常及恢复历史 | 编排异常和后续尝试、恢复结果在自己的详情可查看，普通业务尝试不复制进 DAG 历史 |
| 嵌套与祖先 DAG 错误 | 错误归属实际负责的 DAG；尚未创建的下游位置仍有可理解定位，不错误导航到不存在实例 |
| 同定义多实例与逐项展开 | 各实例分别保留自己的历史、输入、结果和原生地址，编号与操作不串用 |
| 重复操作与独立分支并行 | 同节点在途重复请求不重复执行或增加业务记录，不同分支结果及历史均保留 |
| 执行中断后重启 | 未确定结果显示未知，保留已保存证据；未经明确重新执行不启动新业务 |
| 待确认及成功结果后重启 | 待确认仍需人工确认；已接受成功结果只恢复交付，不重跑业务；既有历史仍可查看 |
| 开始记录保存失败 | 界面明确反馈，命令或 Agent 业务调用次数为零，不产生业务副作用 |
| 业务结果保存失败 | 不报告结果已接受、不推进 DAG，恢复依据最后可靠事实显示未知，不把内存结果当成可靠结果 |
| DAG 新状态保存失败 | 业务成功结果保留，显示交付失败；存储恢复后手动或恢复重交可成功且业务调用次数不增加 |
| 错误记录也无法保存 | 当前界面反馈可获知的失败，不伪造重启后不存在的历史，不进入后台保存重试循环 |
| 实例删除 | 实例及其历史一起删除，宿主原生会话的独立生命周期沿用既有行为 |
| 语言、主题、窄屏与键盘 | 中英文文案正确，深浅主题与窄屏下摘要、展开内容和入口可读；键盘可展开、导航，焦点和禁用原因可辨认 |

实施时先运行对应新增用例，再运行受影响的既有用例及项目检查。E2E 类型检查不能替代真实宿主运行；自动化、真实宿主、确定性模型与未验证项分别报告。实际结论、失败和未验证项见验收记录，不在本规格累积历轮流水账。

## Out of Scope

- 工作流实例级异常中心、跨节点汇总面板，以及普通节点与 DAG 历史之间的关联展示、双向跳转或业务尝试内嵌 DAG 提交历史。
- 新增占用金刚位的通用历史按钮；详情内执行业务、确认、重试、编辑结果或将旧结果重新生效。
- 通用自动重试、定时重交循环、后台保存重试系统、重试次数或退避策略、额外调度框架，以及重跑已完成 DAG 节点。
- 修改已接受结果、实例定义热修复、工作流回退、通过修改源模板改变既有实例快照，或保证确定性编排错误可通过原样重交恢复。
- 旧持久化格式兼容、实例迁移、旧历史补齐或根据残留日志猜测次数和时间；不据此自动删除现有实例。
- 复制工作区文件、完整宿主会话内容、自建 Agent trace、恢复宿主已截断的日志或保证存储故障下完整诊断永不丢失。
- 服务端表单草稿、跨页面草稿同步、填写过程中的输入校验历史，以及新增业务校验语法。
- 改变现有 DAG 依赖、数据契约、条件、展开、聚合、递归、事务回滚或节点业务完成规则。
- 完整正常 DAG 过程追踪、运行历史导出平台、额外权限或处理人员角色管理。
- 升级固定宿主版本、内置或安装 dsh CLI、建立发布分发流程、引入无实际需求的目录或抽象。
