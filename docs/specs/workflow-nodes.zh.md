# 工作流节点真实执行规格

状态：已确认，待实现。本文是本期实现与代码审查的验收依据，不表示功能已经交付。

后续阶段说明：本文保留 chat/bash 真实执行阶段的原始范围。后续[节点模块契约与表单节点规格](./node-modules.zh.md)替代本文中的节点组织、全局字段排他、统一公共启动策略、固定节点界面及旧实例兼容要求；chat/bash 的既有业务行为和占位输出继续保留。后续实施以新规格的范围及其引用 ADR 为准，不将本文历史约束用于否决已确认的新设计。

## Problem Statement

工作流工坊已经能解析 DAG、创建工作流实例、保存实例运行图，并通过手动提交占位输出推进节点。但用户点击“执行”时，并不会创建真实的 dsh 对话或运行沙箱命令，因此工作流尚不能承载实际任务。

现有 DAG 只定义编排结构和输入输出契约，缺少内置工作流节点的字段归属及校验规则。用户需要明确哪些字段属于全部节点、哪些只属于 chat 或 bash，同时继续允许与内置节点能力无关的自定义字段。

本期需要接入真实执行，并以现有节点实例和操作形成闭环。真实业务结果如何构造、交付给下游以及驱动条件与展开，留待后续实现；不为这一步提前建立通用验收、重试或执行历史体系。

## Solution

在现有普通节点定义上加入显式必填的 `node_kind`，当前只支持 `chat` 和 `bash`，以及默认关闭的公共开关 `is_auto_start`。chat 的专属字段是字符串 `prompt`，bash 的专属字段是字符串 `command`，两者在所属节点上必填但允许空内容。

chat 节点实例创建独立的真实 dsh 对话，用户通过宿主界面继续交互，并手动标记工作流节点完成。bash 节点在 dsh 沙箱中执行命令，成功后完成，失败后展示错误，用户可以复用“执行”按钮再次尝试。互不依赖的自动节点允许并行启动，同一个节点实例禁止重复启动。

本期在 bash 成功或用户完成 chat 后，仍复用现有占位输出推进 DAG。真实命令输出和聊天内容只用于用户查看，不参与 DAG 数据传递。执行详情复用现有抽屉，仅展示最后一次执行情况。

## User Stories

1. 作为模板作者，我希望继续使用现有 DAG 编排字段，以便增加真实执行时不用重写图结构和输入输出契约。
2. 作为模板作者，我希望必须明确填写节点族，以便配置能够确定节点执行什么业务能力。
3. 作为模板作者，我希望当前只接受 chat 和 bash，以便未知节点族不会被猜测或静默执行。
4. 作为模板作者，我希望公共字段由基础定义统一声明，以便不同节点族复用相同含义的配置。
5. 作为节点功能开发者，我希望不同节点族不能重复声明同名专属字段，以便字段归属唯一且可检测。
6. 作为模板作者，我希望 chat 使用 bash 专属字段或反向使用时报错，以便及时发现配置放错位置。
7. 作为模板作者，我希望完全未知的字段被原样保留但不解释，以便继续附加自定义信息。
8. 作为模板作者，我希望 chat 必须提供字符串 prompt，以便对话启动内容的结构明确。
9. 作为模板作者，我希望 bash 必须提供字符串 command，以便命令执行配置的结构明确。
10. 作为模板作者，我希望空字符串和纯空白字符串合法，以便有意配置空对话或空操作。
11. 作为模板作者，我希望缺失、null 和错误类型被拒绝，以便允许空内容不等于允许任意配置结构。
12. 作为模板作者，我希望自动启动默认关闭，以便未显式开启的节点仍由用户手动推进。
13. 作为模板作者，我希望自动启动只接受布尔值，以便字符串或数字不会被隐式转换成开关。
14. 作为工作流使用者，我希望点击“执行”只启动选中的节点实例，以便控制当前执行对象。
15. 作为工作流使用者，我希望开启自动启动的节点首次就绪后自行启动，以便减少重复点击。
16. 作为工作流使用者，我希望互不依赖的就绪节点可以并行执行，以便等待一个对话时不阻塞其他分支。
17. 作为工作流使用者，我希望重复点击或并发请求不会重复启动同一节点实例，以便避免重复命令和重复对话。
18. 作为工作流使用者，我希望自动启动失败后不会反复触发，以便由我决定是否再次尝试。
19. 作为工作流使用者，我希望 bash 使用真实 dsh 沙箱执行命令，以便工作流能够执行实际任务。
20. 作为工作流使用者，我希望 bash 空命令作为空操作成功结束，以便空配置也有明确行为。
21. 作为工作流使用者，我希望 bash 成功后直接完成节点，以便不增加不必要的人工验收步骤。
22. 作为工作流使用者，我希望 bash 失败时显示错误且不推进下游，以便失败不会被误认为成功。
23. 作为工作流使用者，我希望失败后仍使用现有“执行”按钮再次尝试，以便不用学习独立的重试操作。
24. 作为工作流使用者，我希望每个 chat 节点实例关联一个独立对话，以便不同任务不混入同一聊天历史。
25. 作为工作流使用者，我希望 for 展开的各个 chat 节点实例分别拥有对话，以便逐项处理不同任务。
26. 作为工作流使用者，我希望非空 prompt 被发送到真实 dsh 对话，以便启动配置中的任务。
27. 作为工作流使用者，我希望空白 prompt 只创建对话而不发送消息，以便进入对话后自行开始交流。
28. 作为工作流使用者，我希望重新打开节点时进入原对话，以便延续已有上下文。
29. 作为工作流使用者，我希望只有我能标记 chat 任务完成，以便一轮回复结束不会被误认为整个任务完成。
30. 作为工作流使用者，我希望会话创建后可自行决定何时标记完成，以便不被额外的会话空闲条件限制。
31. 作为工作流使用者，我希望标记节点完成不会自动取消或关闭对话，以便工作流推进与聊天会话保持各自的生命周期。
32. 作为工作流使用者，我希望真实执行完成后仍能推进现有 DAG，以便本期即可体验完整的执行流程。
33. 作为工作流使用者，我希望清楚知道本期 if 和 for 仍使用占位值，以便不会误以为命令或聊天已经驱动了下游业务数据。
34. 作为工作流使用者，我希望命令成功但 DAG 提交失败后只重新提交结果，以便不会重复产生命令副作用。
35. 作为工作流使用者，我希望重启后保留已记录的成功事实，以便恢复时不重复执行成功命令。
36. 作为工作流使用者，我希望重启后无法确定命令结果时得到明确提示，以便自行决定是否再次执行。
37. 作为工作流使用者，我希望恢复 chat 时不重复创建对话或发送初始 prompt，以便避免重复任务。
38. 作为工作流使用者，我希望 bash 执行期间暂时禁止删除所属实例，以便不会丢失仍在运行任务的工作流记录。
39. 作为工作流使用者，我希望 bash 执行结束后可以删除实例，以便继续使用现有实例管理能力。
40. 作为工作流使用者，我希望删除工作流实例不删除宿主对话，以便聊天记录不会被连带清除。
41. 作为工作流使用者，我希望在现有节点详情抽屉打开对话和完成 chat，以便沿用熟悉的界面。
42. 作为工作流使用者，我希望在 bash 详情中看到命令、执行提示及最终输出或错误，以便了解最后一次执行发生了什么。
43. 作为工作流使用者，我希望详情只展示最后一次执行情况，以便本期不增加执行历史管理的复杂度。
44. 作为模板作者，我希望内置模板的既有 chat 文本迁移为 prompt，以便保留原有任务内容并使用新能力。
45. 作为模板作者，我希望不合规的自定义模板给出明确配置错误，以便按新规则修正后再创建实例。
46. 作为工作流使用者，我希望旧实例的模板快照保持不变并仍可查看，以便历史运行记录不会被迁移改写。
47. 作为工作流使用者，我希望不符合新规则的旧实例提示重新创建并禁止继续执行，以便不会运行含义不明确的配置。
48. 作为工作流使用者，我希望新增操作沿用宿主样式、语言和键盘交互约定，以便在浅色、深色、中英文和窄屏下都能正常使用。

## Implementation Decisions

- **保持现有边界。** DAG 引擎继续负责结构编译、依赖判定、输入输出校验与结果提交；工作流业务层负责内置节点字段校验、真实执行和执行情况保存。chat 和 bash 只服务于工作流，不提供脱离工作流的独立执行接口。
- **定义层面的继承。** 普通节点继续拥有 `id`、`type`、可选输入输出 Schema 等编排字段，`type` 保持 `node`、`dag`、`edge` 的结构语义。公共业务字段与节点族专属字段组合为节点定义，不要求执行行为沿父类、子类链调用。
- **业务类型。** `node_kind` 必填且必须是字符串，当前只接受 `chat` 或 `bash`；缺失、错误类型及未知取值都报错，不根据其他字段推断。未来允许增加节点族，但不为尚未实现的节点族提前提供扩展框架。
- **字段归属。** 公共字段统一声明；不同节点族重复声明同名专属字段属于节点族定义冲突，即使用户配置未使用该字段也要发现。配置引用其他节点族的专属字段必须拒绝，完全未知的字段原样保留，不赋予业务或编排语义。
- **字段值。** chat 的 `prompt`、bash 的 `command` 各自必填且必须为字符串，允许空字符串和纯空白字符串；不接受省略、null 或其他类型，不转换或裁剪原始内容。`is_auto_start` 可省略，默认 false，显式提供时只接受布尔值。
- **启动。** 手动执行只作用于选中的就绪节点实例；自动启动作用于首次就绪且开启该开关的实例。互不依赖的节点可并行，但同一节点实例只能有一个启动过程。失败后不因仍处于可执行前沿而反复自动启动。
- **宿主集成。** 固定适配 dsh 0.2.0-rc.1，复用真实宿主对话、工作区、沙箱和会话导航能力。bash 必须经宿主沙箱执行，不能以普通本地进程替代。仅开发插件，不内置或安装 dsh CLI；后续宿主版本升级另行安排。
- **bash 完成。** 非空命令使用沙箱执行，空白命令作为空操作成功结束。执行成功才进入 DAG 结果提交；非零退出或其他执行错误不推进下游。成功不是仅指宿主调用返回了 Promise 结果，必须依据宿主执行结果判断。
- **chat 关联。** 每个节点实例拥有独立的宿主对话，包括 for 展开的各实例。重复打开使用原对话；已有对话关联不得因重复操作或错误处理而另建。非空 prompt 通过宿主发送，空白 prompt 只创建对话，不发送初始消息。
- **chat 完成。** 对话创建后，用户显式标记节点任务完成；不以消息发送回执、单轮回复结束或会话空闲自动完成。人工完成不要求对话停止生成，也不自动取消或关闭宿主对话。
- **不设通用验收。** 基础节点只保留 `is_auto_start`，不提供 `is_auto_finish`，不增加所有节点共有的人工验收阶段或等待对话空闲阶段。
- **占位推进。** bash 成功或用户完成 chat 后，复用现有运行时按节点输出声明生成占位输出并提交 DAG；提交仍受引擎既有校验和回滚规则约束。本期 if、for 根据占位值判定，不使用真实命令输出或聊天内容，也不构造下游真实业务数据。
- **最小执行记录。** 复用现有节点实例和实例持久化能力，仅保存最后一次执行所需事实、错误及对话关联。不建立独立的重试实体、重试状态、专门重试按钮或历史列表。执行失败保留错误，用户复用“执行”按钮再次尝试。
- **区分执行与提交。** 业务动作已经成功但 DAG 提交失败时，后续尝试仅重新提交占位结果，不重复执行成功命令。这一区分需要在重启后仍成立，不能仅依赖内存或按钮禁用。
- **重启恢复。** 已保存的成功事实用于继续提交 DAG；已启动但未保存结果的 bash 显示“上次执行结果未知”，不自动重跑，也不推断为未执行或已失败，由用户决定是否再次执行。chat 恢复原对话关联，不重复创建或自动重复发送初始 prompt。
- **删除。** bash 正在执行时服务端拒绝删除所属工作流实例，执行结束后恢复删除能力。删除工作流实例不删除其曾创建的宿主对话，本期不另行实现取消命令。
- **接口与状态投影。** 扩展现有工作流实例操作边界，支持真实启动、用户完成 chat、最后一次执行情况及配置不兼容提示。服务端核对节点实例身份与可操作性，防止过期或重复请求产生重复启动、重复提交或覆盖并行分支结果；前端展示服务端事实，不独立推断图推进。
- **详情界面。** 复用现有节点详情抽屉，chat 提供“打开对话”和“完成”，聊天内容交由宿主展示；bash 展示命令、执行中的提示和结束后的输出或错误。本期只显示最后一次执行情况，不做实时日志流。保留现有抽屉宽度、画布位置、主题、语言和可访问性行为。
- **模板迁移。** 内置模板的既有 `chat` 字符串迁移为 `prompt`，同时显式声明 `node_kind: chat`，保留原始任务内容。自定义模板必须满足新规则，不引入旧字段的执行兼容分支。
- **旧实例。** 不迁移已保存实例的模板快照。不符合新规则的旧实例仍可查看，禁止继续执行并提示重新创建；不删除旧实例或改写其历史含义。
- **文档同步。** 实现交付时同步用户可见的配置说明与试用说明，明确真实执行已接入但业务结果仍未参与 DAG 数据传递。本规格和领域决策不能被实现阶段自行删改以规避验收要求。

## Testing Decisions

- **主要测试边界是既有工作流实例 HTTP 集成入口。** 从创建实例、启动节点、用户完成 chat、读取详情、删除和重启恢复等公开操作验证行为，复用当前真实临时存储与宿主服务注入方式，不为测试新增一套执行框架或内部服务接口。
- **只测试外部行为。** 断言节点是否实际启动、宿主调用对应哪个工作区和节点实例、图是否推进、持久事实是否恢复、用户看到什么错误，以及是否发生重复副作用。避免断言私有函数、类继承结构、内部队列形状或纯粹镜像实现的测试。
- **配置覆盖。** 经现有模板读取和实例创建入口，覆盖节点族缺失或未知、必填字段缺失或类型错误、空白内容、开关默认值、跨节点族专属字段误用以及未知字段保留。重复专属字段声明的检测优先纳入该公开校验边界，不为了测试私有实现新增生产接口。
- **真实执行调用覆盖。** 在既有宿主服务注入点控制对话与沙箱的返回和完成时机，覆盖 bash 成功、非零退出、执行错误和空操作；chat 创建、非空初始消息、空 prompt、重复打开、手动完成与 for 实例独立会话。验证宿主发送回执或单轮结束不会自动完成 chat。
- **并发覆盖。** 用可控的未完成宿主调用证明无依赖节点可并行，同一实例不会因重复请求或自动/手动触发重叠而重复启动；不同分支完成不会丢失图变更或已有抽屉宽度偏好。失败后的自动启动不能形成重试循环。
- **持久化覆盖。** 复用现有真实存储重启用例，验证成功执行后提交失败的恢复不重跑命令、结果未知的命令不自动重跑、chat 原关联恢复且不重复发送初始 prompt。不要只用内存状态模拟重启。
- **DAG 回归。** 保持已有输出契约校验、提交回滚、条件边、零项与非空 for、实例身份、聚合连接等测试；确认本期推进仍来自占位输出，真实 stdout 和聊天文本不会被隐式接入业务数据传递。
- **管理与兼容覆盖。** 验证执行中的 bash 阻止删除、结束后可删除、删除不连带删除对话；内置模板迁移后有效，旧实例仍可查看但不合规时不能继续执行，且模板快照没有被改写。
- **补充界面测试只走既有组件边界。** 复用当前实例画布和详情抽屉测试方式，检查执行期间防重、错误后再次执行、打开原会话、人工完成、最后一次命令结果和旧实例提示；保持主题、语言、键盘操作及抽屉交互回归，不断言布局坐标或内部状态。
- **固定宿主版本集成核实。** 使用实际 0.2.0-rc.1 的公开接口核实会话创建、消息发送、导航和沙箱执行，进行临时工作区中的最小真实执行验证；模拟宿主的集成测试不能单独证明真实宿主接入正确。若环境无法完成，应如实列出未验证项，不以占位实现代替。
- 实现过程中运行相关单项测试和类型检查，结束后执行项目完整检查。测试先例包括现有工作流实例 HTTP 与持久化测试、宿主插件生命周期测试，以及节点卡片和详情抽屉组件测试。

## Out of Scope

- chat 自动完成判定、通用人工验收阶段及 `is_auto_finish`。
- 下游真实业务数据构造、真实结果交付方式、自动解析命令或聊天结果，以及用这些结果驱动 if、for。
- 工作流之外独立使用 chat/bash 的执行接口。
- 自动重试、独立重试状态或实体、专门重试按钮、执行历史列表、实时日志流、命令取消和重跑已完成节点。
- 自动迁移旧实例快照、兼容旧业务配置执行，或随工作流删除宿主对话。
- 为未来节点族建设通用插件框架、可配置调度体系，或要求执行行为沿继承链调用。
- 升级 dsh、安装或内置 dsh CLI、发布或分发流程，以及将参考代码目录纳入 Git。
