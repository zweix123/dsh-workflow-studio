# 节点模块契约与表单节点规格

状态：正式规格，待实施。本规格由已确认的设计讨论整理，作为本期实现与验收依据，不表示功能已经交付。测试边界已确认，并明确包含真实 dsh 宿主端到端验收。

## Problem Statement

目前 chat 和 bash 虽然各自有独立的执行函数，但配置校验、启动与完成规则、恢复逻辑、执行记录和界面仍分散在工作流引擎、存储协议及公共页面中。开发者新增一种节点时，必须修改多处按 kind 分支的代码，无法只按稳定契约开发自己的功能。

form 表单节点暴露了这个问题：它需要自己的前端、用户输入、提交校验和真实输出，不能仅被表达为一个运行后返回的服务端函数。未来节点还可能拥有不同的界面与交互方式，框架不能围绕表单或固定的卡片、抽屉内容预设业务界面。

全局排他的节点配置字段也妨碍独立开发。一个节点定义已经通过唯一的 kind 选择实现，另一个无关 kind 使用同名业务字段，不应改变当前配置的合法性。

用户需要一个仍只安装 studio 的工作流工坊：节点模块可以独立开发，节点自行决定是否把启动和结束的控制权交给用户；工作流统一负责编排与可靠保存；工作流执行过程中可以通过表单收集用户输入并继续下游。

## Solution

将 chat、bash 和新建的 form 分别组织为独立的节点包，由唯一的 studio 插件统一装配。公共节点契约归属于 studio，由节点包和 studio 的调用方共同使用，不增加独立契约包，也不引入独立节点插件安装流程。

每个节点拥有自己的配置校验、服务端业务、必要的持久状态、恢复规则和完整前端。studio 提供界面挂载、通用动作通道和持久化协调，不解释节点内部的表单、会话或命令业务。节点是否开放启动、完成或取消操作，由节点决定；未开放的操作不能通过绕过界面直接请求服务端来执行。

服务端围绕就绪、动作、恢复三类入口协作。节点业务完成后报告确定的结果，由工作流保存并提交 DAG。成功完成与取消或中止分开表达，取消不作为成功结果推进下游，也不要求所有节点都支持取消。

本期实际交付最小 form：默认根据输出契约生成表单，按需补充现有 Schema 与界面约定；用户填写并提交后，经过服务端校验的真实结果进入下游。草稿只存在当前工作流页面，正式提交后只读。chat/bash 的代码组织与职责迁移到节点包，既有业务行为和占位输出保持不变。本期不做旧实例兼容或迁移。

## User Stories

1. 作为节点开发者，我希望每种节点类型拥有独立的代码包，以便集中开发和维护它的完整功能。
2. 作为节点开发者，我希望同一个节点包可以包含服务端和前端，以便节点交互不会散落在工坊公共页面中。
3. 作为节点开发者，我希望服务端与浏览器端有分开的入口，以便前端不会加载仅能在服务端运行的依赖。
4. 作为节点开发者，我希望公共契约由 studio 提供，以便与框架使用同一套约定而不再增加契约包。
5. 作为节点开发者，我希望按契约增加节点并完成装配登记后即可接入，以便不用修改工作流或公共页面中的特定 kind 业务分支。
6. 作为节点开发者，我希望节点不依赖工作流、DAG 或存储内部实现，以便独立维护节点业务。
7. 作为节点开发者，我希望可以声明并使用固定版本 dsh 的公开服务，以便无需等待 studio 为每种宿主能力再封装一次。
8. 作为节点开发者，我希望自己的业务状态由框架统一保存，以便获得工作流已有的持久化协调能力。
9. 作为节点开发者，我希望自己决定哪些状态提供给前端，以便无需暴露全部内部执行信息。
10. 作为节点开发者，我希望自己的恢复逻辑处理已保存的业务状态，以便无需让工作流理解每一种业务阶段。
11. 作为节点开发者，我希望自己的界面完全决定内容和交互，以便实现表单以外的不同节点体验。
12. 作为节点开发者，我希望 studio 提供挂载和画布协作能力，以便完整的节点界面能够接入既有工坊。
13. 作为节点开发者，我希望节点前后端使用通用动作通道，以便不用为每种节点重复实现实例定位与持久化协调。
14. 作为节点开发者，我希望动作名称、参数和业务校验由节点定义，以便公共框架不必解释节点专属操作。
15. 作为节点开发者，我希望不同 kind 可以使用同名业务配置字段，以便节点之间不会争夺字段名。
16. 作为模板作者，我希望每个节点通过明确的 kind 选择实现，以便配置不会根据其他字段被猜测执行。
17. 作为节点开发者，我希望重复 kind 被明确识别，以便不会出现实现被静默覆盖的情况。
18. 作为模板作者，我希望公共编排字段保持稳定语义，以便节点扩展不会改变图结构或输入输出契约的含义。
19. 作为模板作者，我希望未知的自定义配置字段继续保留，以便附加信息不会因新增节点类型而突然失效。
20. 作为模板作者，我希望当前节点的必需字段和已知字段类型仍被校验，以便配置错误不会延迟到执行中才被发现。
21. 作为节点开发者，我希望在依赖满足时收到就绪通知，以便自行决定立即执行还是等待用户操作。
22. 作为节点开发者，我希望自行决定是否把启动控制权交给用户，以便支持人工触发和自动执行两种业务。
23. 作为节点开发者，我希望自行决定是否把结束相关操作权交给用户，以便完成条件符合节点本身的业务。
24. 作为工作流使用者，我希望只能执行节点实际允许的操作，以便界面按钮与服务端接受的行为保持一致。
25. 作为节点开发者，我希望框架不强制提供统一的开始和完成按钮，以便不同节点不必套用同一套交互流程。
26. 作为节点开发者，我希望界面操作的业务含义由节点定义，以便框架不会把打开或关闭界面统一当作启动或结束。
27. 作为工作流使用者，我希望成功完成与取消或中止有不同含义，以便被停止的任务不会错误地推进下游。
28. 作为节点开发者，我希望不必实现本节点不支持的取消能力，以便保留明确且真实的能力范围。
29. 作为工作流使用者，我希望独立节点可以并行推进，以便一个等待输入的节点不阻塞其他分支。
30. 作为工作流使用者，我希望重复或过期的动作不会重复执行副作用或完成节点，以便多次点击不会破坏运行状态。
31. 作为工作流使用者，我希望不同分支的状态保存不会相互覆盖，以便并行执行结果保持完整。
32. 作为工作流使用者，我希望业务已完成但 DAG 提交失败时保留完成结果，以便重试提交无需重做业务。
33. 作为工作流使用者，我希望服务重启后恢复已保存事实，以便不把结果未知的操作误认为成功或自动重跑。
34. 作为模板作者，我希望能够使用实际的 form 节点，以便在工作流中收集人工输入而不只验证一个设计示例。
35. 作为模板作者，我希望基础表单只需输出契约即可生成，以便不再重复编写一份字段类型清单。
36. 作为模板作者，我希望表单支持字符串、数字和布尔值，以便覆盖第一版常见的人工输入需求。
37. 作为工作流使用者，我希望可以使用单行、多行、数字、开关和单选控件，以便按数据特点填写内容。
38. 作为模板作者，我希望使用可选的 schema 补充标题、说明、默认值和选项，以便沿用既有关键词而不学习新的字段语言。
39. 作为模板作者，我希望使用可选的 uiSchema 指定必要的控件展示，以便简单表单保持零额外配置。
40. 作为模板作者，我希望不支持的表单类型或控件得到明确错误，以便不会把未实现能力误认为可用。
41. 作为模板作者，我希望表单字段与输出契约保持一致，以便填写结果能够满足下游数据要求。
42. 作为模板作者，我希望表单的额外校验与默认值不改变 DAG 的公共规则，以便其他节点仍按原有契约运行。
43. 作为工作流使用者，我希望没有上游业务输入时也能填写表单，以便在流程中提供新的信息。
44. 作为工作流使用者，我希望上游同名字段可以预填表单，以便无需重复输入已有内容。
45. 作为模板作者，我希望预填采用同名字段规则，以便不再维护额外的映射表达式。
46. 作为工作流使用者，我希望修改预填值不会改写上游原始输入，以便输入来源与最终提交结果可以区分。
47. 作为工作流使用者，我希望上游字段缺失时使用配置的默认值，以便减少重复填写。
48. 作为工作流使用者，我希望上游和默认值均不存在时能自行填写，以便不会得到框架猜测的业务值。
49. 作为工作流使用者，我希望已有的页面草稿优先于初始值，以便重新打开表单不会覆盖我的编辑。
50. 作为模板作者，我希望数字零、布尔假和空字符串都被视为已提供的值，以便它们不会被默认值意外替换。
51. 作为模板作者，我希望类型不匹配的预填值不会被隐式转换，以便配置错误不会改变业务含义。
52. 作为工作流使用者，我希望填写过程只保留在当前页面，以便草稿不被当成正式业务结果保存或传播。
53. 作为工作流使用者，我希望关闭表单浮窗不会完成节点，以便可以稍后继续填写。
54. 作为工作流使用者，我希望同一工作流页面内切换节点后仍保留草稿，以便查看其他内容不会丢失本次编辑。
55. 作为工作流使用者，我希望刷新或离开工作流页面后重新从初始值开始，以便草稿的生命周期明确且仅限当前页面。
56. 作为工作流使用者，我希望不同表单节点实例各有自己的草稿，以便逐项展开的任务不会相互串用输入。
57. 作为工作流使用者，我希望提交由服务端校验，以便绕过界面的无效数据也不会进入下游。
58. 作为工作流使用者，我希望提交校验失败后仍可在当前页面修改内容，以便不必重新填写整份表单。
59. 作为工作流使用者，我希望有效提交产生真实输出，以便下游能使用我填写的数据。
60. 作为模板作者，我希望表单不隐式透传所有上游字段，以便额外数据不会引入下游字段冲突。
61. 作为工作流使用者，我希望首次成功接受的提交成为确定结果，以便其他页面的旧内容不能覆盖它。
62. 作为工作流使用者，我希望重复提交不会重复推进 DAG，以便网络重试或连续点击不会改变已完成事实。
63. 作为工作流使用者，我希望完成后的表单可查看但不可修改，以便已运行下游所使用的数据保持稳定。
64. 作为工作流使用者，我希望结果提交失败时可以重试已接受的结果，以便不需要重新输入或覆盖原结果。
65. 作为工作流使用者，我希望 form 不要求额外点击无业务意义的开始按钮，以便打开、填写、提交即可完成任务。
66. 作为工作流使用者，我希望修正已经提交的数据时通过新的工作流实例处理，以便本期不引入隐式回退或重跑。
67. 作为模板作者，我希望 chat 和 bash 的现有配置行为保持不变，以便模块化不会改变模板中已有任务的含义。
68. 作为工作流使用者，我希望 bash 继续通过宿主沙箱执行，以便不绕过既有执行约束。
69. 作为工作流使用者，我希望 bash 成功后完成、失败后不推进并可再次尝试，以便延续既有操作方式。
70. 作为工作流使用者，我希望成功命令在结果提交失败或重启后不会被重复执行，以便避免重复副作用。
71. 作为工作流使用者，我希望 chat 继续关联原有独立会话，以便重新打开节点不会创建重复对话。
72. 作为工作流使用者，我希望 chat 仍由用户明确完成，而不是一轮回复结束就完成，以便对话任务保持原有含义。
73. 作为工作流使用者，我希望 chat 的完成不会自动关闭或取消对话，以便聊天生命周期与工作流推进保持独立。
74. 作为模板作者，我希望 chat/bash 仍提交现有占位输出并被明确说明，以便不误以为这次重构接通了它们的真实业务数据。
75. 作为工作流使用者，我希望 bash 运行中的删除保护和删除实例不删除宿主对话的行为继续保留，以便记录与外部任务保持一致。
76. 作为工作流使用者，我希望只安装一个 studio 插件即可使用本期节点，以便无需分别安装多个 dsh 插件。
77. 作为项目维护者，我希望干净构建能正确解析各包和契约，以便拆包后的项目不依赖旧产物才能构建。
78. 作为项目维护者，我希望浏览器产物使用宿主的既有能力，以便不会因为节点拆包引入服务端依赖或重复运行时。
79. 作为项目维护者，我希望固定适配既定 dsh 版本，以便本期验收不混入宿主升级问题。
80. 作为工作流使用者，我希望节点界面遵守宿主主题、语言和键盘交互约定，以便在深浅主题、中英文和窄屏下仍能使用。
81. 作为项目维护者，我希望本期不承担旧实例迁移或兼容，以便聚焦节点契约和实际表单能力。
82. 作为项目维护者，我希望“不做兼容”不被解释成自动删除旧数据，以便既有文件和宿主对话不会被擅自清理。
83. 作为项目维护者，我希望沿用现有集成与界面测试入口，以便验收外部行为而不是建立另一套测试框架。
84. 作为项目维护者，我希望补充真实宿主端到端验收，以便证明实际插件、界面、沙箱和聊天服务能够协作。
85. 作为项目维护者，我希望真实环境无法完成的验收被明确标为未验证，以便模拟测试不会被误报为宿主集成已通过。

## Implementation Decisions

- **单一插件、独立节点包。** chat、bash、form 各自作为 workspace 中的独立包，由 studio 装配。节点包不是独立的 dsh 插件，不建立单独安装、发布或动态插件管理流程。新增节点所需的依赖与登记属于装配，不应继续在引擎、存储或公共页面增加针对该 kind 的业务分支。
- **契约归属于 studio。** 公共节点契约在 studio 内提供独立入口，位置与依赖方向遵循 ADR 0003，不单独建立契约包。studio 的使用方与节点包共用该契约；契约不反向依赖具体节点、工作流、DAG 或存储实现。节点也不依赖其他节点的内部实现。
- **前后端分开加载。** 每个节点提供清晰的服务端和前端入口，业务私有协议保留在节点内部。构建需保证干净环境中可以解析契约并完成类型检查，且最终仅安装 studio 就能加载本期全部节点；不能依赖残留产物或把工作区包名留成用户未安装的运行时依赖。类型导入不会自动消除包依赖环，构建顺序需实际验证。
- **复用宿主公开能力。** 固定适配 dsh 0.2.0-rc.1，节点声明需要的公开服务，由装配层注入。允许直接使用固定版本的 dsh 接口，不要求 studio 重包全部宿主能力；不把工作流实例内部状态或存储对象作为通用能力暴露给节点。
- **配置由 kind 解释。** kind 必填、明确、唯一，不通过其他字段猜测实现。公共编排字段由框架校验并保护语义；当前 kind 的业务字段由对应节点校验。不同 kind 可以使用同名字段，取消全局字段排他与跨 kind 字段误用检查。未知配置字段原样保留但不解释，已知字段类型错误和必需字段缺失仍报错。
- **三类服务端入口。** 就绪入口接收依赖满足后的通知，动作入口接收转交的用户操作，恢复入口处理服务重启后的已存事实。节点决定实际执行、等待及业务恢复方式，不强迫所有节点沿统一的开始或完成操作链运行。通知、恢复和并发动作不得导致重复副作用。
- **控制权属于节点。** 节点决定是否向用户开放启动、成功完成或取消等操作，也可以保留控制权。界面只展示与节点能力和当前状态一致的操作；服务端仍由节点校验动作，不得仅靠按钮隐藏阻止未开放操作。框架不自行增设所有节点共有的自动开始、自动结束或人工验收开关。
- **界面事件没有统一业务含义。** 框架不把打开或关闭界面直接等同于启动或结束；节点可以自行定义这种关联。本期 form 关闭浮窗只收起界面，不完成节点；chat/bash 保留既有行为。
- **成功与取消分开。** 节点业务完成产生确定结果，由工作流提交 DAG；节点取消或中止不视为成功，不以成功结果推进下游。节点决定是否支持以及是否开放这些能力。本期不因契约能表达取消就给 chat/bash 新增取消功能，也不增加统一取消按钮。
- **通用动作通道。** studio 负责定位实例、核对可操作性、转交动作以及并发和持久化协调；节点负责动作名称、参数和业务状态校验。相同节点实例的重复或过期请求不能重复完成、覆盖已接受结果或触发重复副作用；独立分支仍可并行。
- **节点业务状态与持久化分工。** 节点定义需要保存的可序列化业务状态，并决定对前端的投影。studio 只解释公共执行阶段、错误与完成结果，统一保存状态，不理解会话阶段、命令输出等具体业务字段。恢复由节点实现，恢复进展仍经框架保存；纯前端临时状态不要求进入持久化。
- **完成事实与 DAG 提交分开。** 先校验并保存被接受的业务结果，再协调 DAG 提交。DAG 提交失败不抹去业务完成事实，后续重试使用已保存结果；保存失败不得声称已接受提交。重启后不能重做已确认成功的副作用，也不能推断结果未知的外部任务已经成功。保留现有 DAG 校验、回滚、分支与实例身份语义。
- **完整节点前端。** studio 提供挂载位置、图布局与必要的交互协作，节点拥有挂载区域内的完整内容、操作和浮窗。不能将节点限制为固定业务卡片或抽屉中的字段插槽，也不能把 form 的控件清单变成所有节点的界面契约。节点自行组织本地交互状态并复用宿主主题、组件、语言及可访问性约定。
- **form 的业务流程。** form 就绪后等待用户填写；用户打开节点交互界面后填写并正式提交，不强制增加独立开始步骤。服务端校验通过的提交产生真实输出并完成业务，校验失败保留当前页面的编辑内容并显示错误，不能推进下游。
- **form 字段来源。** 输出字段及其类型以 output_schema 为准，基础表单自动生成，不要求额外 fields，也不重复声明字段类型。input_schema 仅描述真正的上游数据依赖，不能因为某字段将由用户填写就把它声明为必需的上游来源。
- **form 第一版能力。** 支持字符串、数字和布尔值，以及单行、多行、数字、开关和单选控件。不支持嵌套对象、可增删数组和文件上传；不支持的类型、控件或配置明确报错。此限制仅属于 form，不限制节点公共契约。
- **表单语法采用既有约定。** 可选 schema 使用 properties 下的 title、description、default、enum 等已确认用途的 JSON Schema 关键词，可选 uiSchema 使用 RJSF 展示约定，包括用 ui:widget 指定多行文本。基础类型来自输出契约，展示或约束配置必须与其一致。本期只实现上述控件所需的明确子集，并在用户说明中列出支持表；不宣称支持完整 JSON Schema，不另造 label、widget、options 字段语言，也不预先要求引入整个表单库。
- **表单校验与 DAG 校验分工。** form 的补充 Schema、控件选择、枚举及默认值由 form 校验，不能改变其他节点的 DAG 语义。输出契约要求声明字段存在且类型正确；字段存在不等于字符串非空。已声明的表单规则须在服务端同样执行，不得只做浏览器校验。
- **预填与初始值。** 当前工作流页面已有草稿时保留整份草稿。首次初始化时，逐字段使用上游同名值，其次使用配置的 default，均不存在时显示空控件等待填写。按字段是否存在判断，不把零、假或空字符串当成缺失；预填值不得隐式转换类型，不引入额外映射表达式，不改写原始输入。
- **草稿仅在页面内。** form 自行管理每个节点实例的草稿。同一工作流页面中切换节点、关闭并重开浮窗时保留；刷新或离开该工作流页面时丢弃。不向服务端自动保存，不使用跨页面草稿同步、草稿版本冲突检测或持久化恢复。界面挂载方式必须满足这些可观察行为。
- **提交即确定结果。** 以服务端首次成功接受的有效提交为准。不同页面可以有不同的本地草稿，但后续请求不能覆盖已接受的结果或重复推进 DAG。完成后允许查看结果，不允许编辑；DAG 提交失败时仍重试已接受结果，不重新开放业务数据编辑。本期没有回退或已完成节点重跑。
- **form 输出范围。** 输出来自通过校验的正式提交，符合输出契约；上游其他字段和编辑过程中的草稿不隐式混入。允许输入与输出不同，同一定义逐项展开后的各节点实例独立处理自己的输入、草稿与结果。
- **chat 保持行为。** 每个节点实例关联独立会话，重新打开复用原会话，非空 prompt 按原行为发送，空白 prompt 只创建会话。保留会话与发送进展的恢复，不重复创建或自动重复发送初始内容。用户明确完成，不以回复结束或会话空闲自动完成，也不因工作流完成自动关闭对话；本期仍提交占位输出。
- **bash 保持行为。** 继续使用真实宿主沙箱；空白命令为空操作，成功后完成，非零退出和执行错误不推进下游。失败后沿用启动操作再次尝试，不新增自动重试；失败的自动启动不形成循环。已确认成功但待 DAG 提交时不重跑，重启后的未知执行结果须明确显示；本期仍提交占位输出并展示最后一次真实执行情况。
- **保留既有管理行为。** chat/bash 现有自动启动配置仍有效，但解释权归节点，不成为所有节点强制支持的公共开关。保留同一节点防重、独立节点并发、执行中 bash 的实例删除保护以及删除实例不删除宿主会话的行为。
- **不做历史兼容。** 本期不迁移旧实例状态，不承诺旧格式继续执行，也不增加旧格式专用查看适配。该范围选择不授权自动删除旧实例文件、改写其模板快照或删除宿主对话。
- **实现阶段同步说明。** 交付时同步节点配置、表单支持范围、真实输出与占位输出差异及宿主使用说明。当前目录结构、代码中的硬编码和旧规格不能用来缩减本规格确认的模块独立性；具体类型名、登记方式和构建步骤在这些约束下选择最小可行实现。

## Testing Decisions

- **测试入口已确认。** 以现有工作流实例 HTTP 集成入口为主要 seam，保留真实临时存储与宿主服务注入方式；补充现有工坊 React 交互测试和插件构建加载检查，并增加真实宿主端到端验收。不新增独立测试框架，不为测试暴露节点内部函数或存储实现。
- **只断言外部行为。** 检查用户可见状态、宿主调用、接受或拒绝的动作、实际下游数据和重启后的事实；不按私有函数、内部状态对象形状、队列实现或文件拆分方式写镜像测试。模块独立性通过公共契约装配后的可运行行为及构建依赖检查证明。
- **配置与接入。** 经现有模板读取、实例创建及公开装配入口验证不同 kind 同名字段可用、当前 kind 的必需字段与类型校验、公共字段保护、未知字段保留，以及重复或不可用 kind 的明确错误。证明增加另一节点类型不会改变已有合法配置的解释。
- **控制权与三类入口。** 经公开操作验证节点就绪后可执行或等待、用户只能触发节点允许的动作、恢复遵守已保存事实。验证成功完成与取消不会被混同；可用最小的测试节点经同一契约证明框架行为，不为生产节点补造尚未支持的取消功能。
- **form 数据链路。** 验证空白表单、同名预填、默认值、页面已有草稿优先、零／假／空字符串、类型不匹配、不支持配置、枚举和服务端提交校验。验证原始输入不变、无关上游字段不进入输出，真实表单结果进入下游并参与既有 DAG 数据流与条件计算。
- **form 页面行为。** 沿用工坊和节点交互测试入口，覆盖控件呈现、输入与提交、错误后的本地编辑保留、关闭和重开浮窗、节点切换、页面退出或刷新后的草稿丢弃，以及完成后只读。验证草稿操作没有服务端自动保存请求，多个节点实例不串用草稿。
- **并发与持久化。** 使用现有 HTTP 测试中的可控未完成宿主调用和真实存储，覆盖同一节点防重、独立分支并行、过期响应不覆盖新状态、两份本地草稿提交只有首个有效结果被接受，以及 DAG 拒绝提交后的结果保存和恢复。重启测试重新创建服务，不能仅在内存中模拟。
- **chat/bash 行为回归。** 复用现有实例集成测试，覆盖真实服务接口调用、空配置、自动与手动启动、失败重试、会话独立性、恢复防重复、人工完成、成功事实与提交分离、未知命令结果、删除保护和不连带删除会话。断言真实执行内容仍未被隐式替换为下游输出；旧实例专用兼容不作为本期验收要求。
- **DAG 与既有界面回归。** 保留当前输出校验和提交回滚、条件边、逐项展开、聚合连接、实例身份及并行分支测试。公共图布局、选择与导航行为仍回归；原先关于固定业务卡片、统一按钮或固定详情正文的断言按新职责调整，不能用旧的内部布局断言限制完整节点前端。
- **构建和插件加载。** 沿用宿主生命周期与浏览器产物加载测试，补充拆包后干净构建、类型产物解析和单一插件加载检查。验证浏览器不引入服务端依赖、宿主提供的前端运行时保持可用，以及节点功能不依赖旧构建缓存或额外安装节点插件。
- **真实宿主端到端验收必须执行。** 在用户已安装的 dsh 0.2.0-rc.1 与隔离的临时工作区中，使用真实 studio 插件、真实浏览器界面、真实宿主会话和沙箱完成验收；不能以模拟宿主的 HTTP 或组件测试替代。不得为验收升级、安装或内置 dsh CLI。
- **真实 form 路径。** 在宿主界面创建含 form 的工作流，打开表单、填写并验证默认值和预填、收起和切换后恢复页面草稿、提交后查看只读结果，并确认真实输入到达下游。再用另一实例验证刷新丢弃未提交草稿，以及无效提交不推进。覆盖中英文、深浅主题、窄屏与必要键盘交互。
- **真实 chat/bash 路径。** 通过实际宿主运行无破坏性的沙箱命令，验证成功、错误展示和占位推进；创建真实 chat 会话并验证初始内容、原会话导航和用户完成。重启宿主后验证本期新建实例的已保存状态，不能把未完成的真实步骤视为通过。
- **验收证据与环境限制。** 记录真实宿主版本、关键操作、观察结果和通过／失败状态，保留必要日志或界面证据。环境缺失、模型调用或沙箱能力不可用时，明确列出未验证项和原因；模拟测试通过不能替代真实验收结论。实施中运行相关测试与类型检查，结束后完成项目检查及已确认的真实宿主验收。

## Out of Scope

- 模板契约、独立契约包、独立 dsh 节点插件、节点市场、动态安装与卸载、单独发布节点包或插件分发流程。
- 为未来节点预建通用业务界面、复杂调度框架、完整插件平台或未使用的扩展能力。
- 全部节点强制支持自动启动、自动结束、人工验收或统一取消操作；本期不新增 chat/bash 的取消能力。
- chat 自动完成判定、聊天结果提取、bash 真实输出映射，以及把 chat/bash 的占位输出改为真实业务数据。
- form 的嵌套对象、可增删数组、文件上传、复杂表单设计器、完整 JSON Schema 实现及新的字段映射表达式。
- 服务端草稿自动保存、浏览器持久化草稿、跨页面或跨设备草稿同步、协同编辑、草稿冲突合并。
- 已完成结果修改、工作流回退、已完成节点重跑、执行历史体系和通用自动重试。
- 旧实例兼容、旧格式查看适配、状态迁移、自动清理旧实例或删除宿主会话。
- 宿主版本升级、安装或内置 dsh CLI，以及将参考实现代码纳入版本管理。
