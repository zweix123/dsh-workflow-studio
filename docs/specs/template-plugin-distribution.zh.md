## 目标与范围

- 新增 `dsh-workflow-template` 包，提供用于加载和注册工作流模板的 dsh 插件。
- 第三方通过自己的 dsh bundle 提供模板；内置模板使用同一套加载与注册机制。
- 打通模板从随包提供、装配加载到工坊使用的完整流程；第三方作者无须编写注册代码。
- 节点扩展机制由[节点插件化注册规格](./node-plugin-registration.zh.md)定义；本文消费工坊已经装配的节点能力，不自行实现节点扩展。
- 继续适配项目固定的 `@deepseek-ai/dsh@0.2.0-rc.1`。
- 原插件化阶段落实加载、登记和工坊行为；后续附属文件扩展仅增加 Bash 对模板目录的引用，不增加资源快照、依赖安装或其他节点的文件引用能力。

## 加载规则

- 模板统一通过插件声明提供，停止将 DSH home 中的旧模板目录作为自动发现入口，也停止向其中复制内置模板。本期不要求兼容旧入口，不自动删除磁盘上的旧模板文件。
- 模板定义只在模板声明自身加载或重新加载时读取。页面查询和创建实例使用已经加载的定义，不因读取页面而重新加载包内 YAML；所需节点类型消失或恢复时，只重新判定当前已读定义的依赖与配置，不重读文件。已有实例仍持有自己的定义快照。
- 模板可见性跟随启用该 bundle 的 dsh profile；同一 profile 中各工作区共享可用模板。此范围仅针对模板库，不改变实例存储的既有作用域。
- 模板使用同一 profile 中装配的节点类型；节点库同样在该 profile 的工作区之间共享，不为不同工作区选择不同的节点实现。
- 第三方模板作者提供 `package.json`、补丁和模板 YAML，可在模板目录中携带脚本、文档和配置等附属文件；定义定位、读取和注册由通用模板插件承担。
- 模板加载时读取 YAML 定义并保留其所在目录；Bash 执行时通过 `DSH_TEMPLATE_DIR` 引用附属文件，工作目录继续为实例所属工作区。附属文件读取执行时的内容，不随 YAML 登记缓存或保存实例副本。
- 使用 `workflow.yaml` 根 `id` 作为模板 ID，根 `name` 作为前端展示名称。目录只用于定位。第三方补丁的 `config` 只指定模板来源路径，不重复声明模板 ID 或名称。
- 同一 profile 内出现相同模板 ID 的多个贡献时，所有冲突项均不可用，显示各自来源；不以加载先后作为优先级。其他模板及已有实例不受影响。
- 来源不存在、YAML 损坏或模板校验失败时，工坊保留加载失败记录并显示来源与原因，其他模板继续可用。无法取得有效名称时，来源路径用于定位错误记录，不作为模板名称的回退。
- 所需节点类型缺失或冲突时，模板在工坊中保留为不可用项，并显示缺失或冲突的类型，不仅依赖宿主插件管理页面说明原因。依赖未满足时不能创建实例；依赖恢复并通过校验后自动恢复可用，不要求用户通过调整插件装配顺序解决。
- 已有实例显示创建时定义中的模板名称，模板改名或卸载不改变它。此行为继承既有快照语义。
- 本次改造前创建的实例不要求继续执行，也不新增旧格式查看适配；旧实例文件不自动删除或改写。内置节点与六份源模板统一改造为符合新规范。本文关于已有实例名称、快照及卸载后读取与恢复的承诺，适用于按新规范创建的实例；不为改造前缺少根 `name` 的旧快照新增名称回退或迁移规则。

- 当前模板 ID 和列表展示名称取自目录名；模板列表、详情与创建实例会读取目录中的定义。见[模板管理规格](./template-management.zh.md)及 `packages/dsh-workflow-studio/src/host/service/workflow-instance-service.ts`。
- 已有工作流实例保存创建时的完整定义，源模板变动不改写实例快照。
- 节点阶段已完成独立公共登记、具体类型依赖及生命周期接口；模板阶段复用 `dsh-workflow-node/contract` 的 `NodeLookup`、`nodeService` 和登记变更通知，不另建节点登记。

## 声明与路径契约

一条补丁声明指向一个模板目录，以该目录中的 `workflow.yaml` 为定义入口。同一个 bundle 可以贡献多个模板。

加载插件的包名为 `dsh-workflow-template`。声明的 `config.directory` 提供带包名的目录资源地址，例如 `@acme/workflows/templates/review`。加载器追加固定的 `/workflow.yaml`，通过当前 profile 的模块解析器定位完整资源地址，再以文件方式读取和解析 YAML；不把 YAML 当作 JavaScript 模块执行。

贡献包必须通过 `package.json` 的 `exports` 暴露对应 `workflow.yaml`。`directory` 是包资源地址，不是相对宿主进程工作目录或补丁文件的文件系统路径。安装位置变化不需要修改地址。

外层 Cordis 声明的 `id` 用于插件装配地址，`name` 用于定位加载插件模块；模板身份和展示名称分别来自 YAML 根 `id`、`name`。因此补丁中不再设置 `config.id` 或 `config.name`。

补丁文件由 `dsh.bundle.patch` 指定，`cordis.patch.yml` 是本项目使用的文件名，不是所有 dsh 插件都必须具有的文件。一个 bundle 可在补丁中声明多个加载插件实例，每个实例指向一个模板目录。

已核实的宿主限制：bundle 补丁解析会锚定相对的插件模块名，但不会自动将普通 `config.directory` 转成相对贡献 bundle 的路径；实现不得假定 `ctx.baseUrl` 指向贡献 bundle。

## 模板附属文件与 Bash 路径契约

本节为 2026-10-08 已确认并实施的扩展规则，验证范围见[附属文件验收记录](../acceptance/template-attached-files.zh.md)。

- **目录来源。** 模板目录为当前 profile 模块解析器返回的 `workflow.yaml` 文件 URL 的父目录，转换为本机绝对路径。以实际解析结果为准，不能从模板 ID、声明字符串或宿主 cwd 推导；`exports` 可以将资源地址映射到另一文件位置。不另加符号链接解引用规则。
- **作者配置。** 复用现有 `config.directory`，不新增 YAML 根字段、节点资源字段、文件清单或固定的 `resources/` 子目录。作者可自行组织 `scripts/`、`docs/` 等子目录，随本地模板包提供文件；只需 exports 暴露 `workflow.yaml`，附属文件不要求逐个 exports。本期不增加 npm 打包或发布流程。
- **执行引用。** 系统为 Bash 命令提供 `DSH_TEMPLATE_DIR`，通过固定 rc.1 的 Shell `dshEnv` 传入，不依赖宿主进程环境中的同名变量。它是执行环境信息，不是 DAG 业务输入，不要求 `input_schema` 声明，也不使用 `{{ DSH_TEMPLATE_DIR }}`。路径引用使用 Shell 双引号，例如 `bash "$DSH_TEMPLATE_DIR/scripts/inspect.sh"`。
- **工作目录与范围。** Bash 的 cwd 和 sandbox `workspaceRoot` 继续使用实例所属工作区；不切换到模板目录。嵌套 DAG、递归和逐项展开中的 Bash 使用同一工作流实例保存的模板目录。本次只支持 Bash，不向 session_agent 提示词或会话注入模板路径。
- **实例来源。** 创建实例时，除保存 YAML 定义快照外，保存模板目录作为内部元数据；执行时经公共节点上下文传给 Bash。节点插件不读取 Studio 的登记或实例存储，也不依赖其内部类型。不把绝对目录改写进 YAML `command`，不根据当前模板登记重新绑定旧实例来源。
- **旧数据。** 内部目录信息允许缺省；扩展前实例没有可靠来源时，不从模板 ID 猜测或自动补回目录，不注入该变量，普通工作区命令继续按原规则执行。使用新增变量的模板需通过扩展后的创建链路产生实例。
- **定义与文件分开。** YAML 修改仍仅在模板声明重载后作用于新实例；旧实例的定义和命令不热更新。包内脚本、文档和配置直接读取执行时的文件：文件 A 改为 B 后，旧实例下次实际执行命令时读取 B，无须重载 YAML。已接受的成功结果继续复用，不因文件变化重跑。
- **撤销、删除与移动。** 仅撤销模板登记不清除已有实例保存的目录；所需节点仍可用且原文件可访问时，实例可继续执行。物理删除、移动包或删除被调用文件可能使相关命令失败；不缓存文件副本、不自动迁移旧实例路径、不回退到其他同 ID 模板。重新加载后的新实例使用新的解析位置。
- **读取与写入。** 附属文件按只读用途约定用于读取或执行，运行产物及状态写入用户工作区，不以修改模板包作为任务步骤。继续沿用宿主现有沙箱和操作系统权限，不提升权限、不关闭沙箱、不新增针对模板目录的强制只读隔离承诺。固定 rc.1 公共沙箱策略没有单独排除可写子目录的接口，因此模板目录位于工作区等可写范围内时，不能声称宿主必然阻止写入。
- **失败边界。** 不静态分析命令、扫描脚本依赖或预先读取全部附属文件。被调用文件缺失、不可读、外部工具未安装或被沙箱拒绝，沿用 Bash 执行错误、日志和人工重试规则；不把某个运行时文件错误扩成整个模板登记失败。外部 CLI 或运行环境由使用者准备，本能力不自动安装依赖。

最小职责链为：加载器保留解析后的目录 → Studio 登记并在实例创建时持久化 → 公共节点执行上下文传递目录 → Bash 注入 `dshEnv`。模板加载器仍不承担节点执行，模板附属文件不进入 DAG 编排或业务输入输出。

## 作者侧完整示例

在已装配工坊和模板加载插件的 profile 中，以下 bundle 通过本地目录添加后提供一个模板；本期不新增 npm 发布流程。

```text
acme-workflows/
├── package.json
├── cordis.patch.yml
└── templates/
    └── review/
        ├── workflow.yaml
        ├── scripts/
        │   └── inspect.sh
        └── docs/
            └── review-guide.md
```

`package.json`：

```json
{
  "name": "@acme/workflows",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
  "exports": {
    "./templates/*/workflow.yaml": "./templates/*/workflow.yaml"
  }
}
```

`cordis.patch.yml`：

```yaml
- insert:
    - id: acme-review-loader
      name: dsh-workflow-template
      config:
        directory: '@acme/workflows/templates/review'
```

`templates/review/workflow.yaml`：

```yaml
id: acme-review
name: 团队代码审查
type: dag
dag:
  - id: inspect
    type: node
    node_kind: bash
    command: bash "$DSH_TEMPLATE_DIR/scripts/inspect.sh"
```

`templates/review/scripts/inspect.sh`：

```sh
#!/usr/bin/env bash
set -e
cat "$DSH_TEMPLATE_DIR/docs/review-guide.md" >&2
git diff --stat
```

说明文档通过模板目录读取；`git diff` 仍针对用户工作区执行。上面的目录及命令示例使用已实现的附属文件引用契约，实际访问仍受宿主沙箱及系统权限约束。

示例中的目录 `review` 与模板 ID `acme-review` 有意不同，以说明二者没有相等要求。补丁只提供来源，模板身份和名称均由 YAML 自身声明。

包名来自贡献 bundle 的 `package.json`。上述 wildcard exports 暴露包内模板定义文件，使加载器可以解析 `@acme/workflows/templates/review/workflow.yaml`。

## 改造前的根 ID 和包内资源核实

- 当前 DAG 编译器要求根 `id` 为字符串，并在单份定义内部检查显式 ID 重复；没有跨模板唯一性检查，也未额外拒绝空字符串。见 `packages/dsh-workflow-studio/src/host/dag/compiler.ts`。
- 当前 `openspec-workflow` 和 `openspec-workflow.zh` 的根 `id` 都是 `openspec-sdd-workflow`。实施时必须消除这对内置模板的 ID 冲突，并在注册入口检查冲突。其余两对内置模板分别使用英文或中文标题作为根 ID。
- 根 `id` 同时参与 DAG 的自递归引用。修改模板根 ID 时，存在的根自引用也必须同步修改。
- 原阶段只从模板目录读取 `workflow.yaml`，未提供包内附属文件的运行时定位；后续扩展规则见[模板附属文件与 Bash 路径契约](#模板附属文件与-bash-路径契约)。Bash 命令的普通相对路径继续基于工作区，session_agent 也在实例工作区创建会话。
- 宿主有按完整包资源地址定位文件的机制；加载插件使用它支持只含声明与 YAML 的模板 bundle。

## 模板身份与展示名称

- `workflow.yaml` 根 `id` 表示稳定的模板身份，必须是非空且非纯空白的字符串，在同一 profile 内唯一。
- `workflow.yaml` 根新增 `name` 表示模板展示名称，必须是非空且非纯空白的字符串。模板级列表、选择器和详情标题统一使用该名称；名称不要求唯一，修改名称不改变模板身份。
- 目录和文件路径仅用于定位定义，不参与模板身份或展示名称。推荐目录名与模板 ID 一致，但不强制校验这一约定。
- 模板作者用模板自身语言编写 `name`；中英文仍是独立模板，分别使用不同的根 `id`。
- `name` 必填，缺失或为空时明确报告模板配置错误，不引入目录名或 ID 的隐式展示回退。
- 第三方 bundle 的补丁配置只提供来源路径；模板 ID 和名称从 YAML 获取，不再提供重复的 `config.id` 或 `config.name`。
- 本规则只定义模板级名称，不改变节点与 DAG 图卡的现有定义 ID 语义。

已有实例的来源模板名称从其保存的定义快照读取，不查询当前模板提供包。

## 生命周期

以下行为由已确认规则直接推出，不另设可切换策略：

- 声明加载时创建模板贡献记录，读取和校验一次定义；工坊查询已加载的注册结果。
- 声明重新加载时，用新内容重新校验该贡献。错误保留为诊断，不将新内容视为有效模板。
- 重载失败沿用固定版本宿主的实际插件生命周期，不新增上一份有效模板的缓存或自动回滚。宿主在开始重载前拒绝新配置时，尚未卸载的旧贡献保持原状态；已经进入卸载和重新加载后，新一轮读取或校验失败不会自动恢复旧贡献。加载器已获得的模板读取与校验错误继续按本文规则保留来源和原因。
- 声明卸载时撤销对应贡献，新实例不能继续选择它；已创建实例仍使用完整定义快照和保存的来源目录。定义快照不保证包内附属文件在物理删除或移动后仍可访问。
- 当造成 ID 冲突的其他贡献被撤销后，剩余的有效贡献恢复可用；注销不能误删相同 ID 下其他声明的贡献。
- 列表、详情与实例创建使用同一注册结果；创建时再次确认该模板当前可用，再保存完整定义快照。
- 不为模板 YAML 建立额外的后台监听或轮询；定义内容变化遵循声明加载和重新加载时机。附属文件不进入定义缓存，命令直接读取其执行时的内容。

模板元数据、DAG 和节点配置错误会使该贡献不可用；现有 `layout` 非阻断诊断继续作为警告展示，不因此阻止模板使用。

## 模块职责与装配流程

- Studio 提供当前 profile 的模板登记与查询能力，统一负责模板元数据、DAG 和已有节点类型的校验、ID 冲突判定，以及工坊与实例创建所使用的可用性结果。
- 新模板加载插件消费上述能力：解析包资源地址、读取 YAML、提交定义及解析后的模板目录或读取失败诊断，并将注销动作绑定到声明自身的生命周期。Studio 将目录保存为实例内部元数据并通过公共节点上下文传递，不要求作者重复配置。
- 第三方 bundle 只提供包资源与加载声明；内置六份模板也使用同一个加载插件和登记入口。
- 默认 bundle 同时装配工坊、公共登记能力、三个内置节点、通用模板加载插件及唯一的内置模板 mattpocock 中文版（`matt-pocock-wayfinder-workflow.zh`），用户不需要逐一添加这些默认组件；第三方 bundle 仍可独立提供模板。
- 通过 Cordis 服务注入保证依赖就绪，不依赖补丁条目的排列顺序。Studio 不在自身初始化中等待依赖自己的所有模板声明完成，宿主负责等待加载树收敛。
- 具体节点类型的可用性接入节点登记能力提供的宿主依赖机制；仅等待登记服务本身不能证明模板所需类型已存在。未满足具体类型依赖时不登记为可创建实例的有效模板，同时保留工坊诊断所需的信息。
- 读取模板资源与等待节点依赖分别协调，不能为了等待某个节点类型而失去不可用模板的诊断，也不能将节点依赖变化误作模板声明自身重载。具体节点依赖依据已读定义确定，作者不在补丁中维护第二份节点类型清单。
- 模板加载插件不承担工作流执行，不引入节点插件扩展机制。实例创建后，执行与恢复继续依赖实例保存的定义。

## 实现后的验收场景

以下为验收要求；逐项实际结果、验证方式与限制见[验收记录](../acceptance/template-plugin-distribution.zh.md)。

1. 在固定 rc.1 宿主中从本地目录添加一个纯配置 bundle，模板出现在所属 profile 下各工作区的选择器中。
2. 目录名与模板 ID 不同仍能加载；UI 显示 YAML 的 `name`，请求与实例关联使用 YAML 的 `id`。
3. 内置六份模板通过相同声明机制加载；补齐展示名称与互不冲突的根 ID，保留中英文独立条目和结构对应关系。
4. 两条声明提供相同模板 ID 时均不可用并可定位来源；移除冲突贡献后，剩余有效模板恢复可用。
5. 文件不可定位、YAML 错误、ID 或名称缺失、为空或仅含空白，以及节点配置无效时，工坊展示失败原因，其他模板与已有实例仍可使用；仅有 `layout` 警告的模板仍可用。
6. 修改包内 YAML 后，仅刷新页面不重读文件；声明重新加载后，新实例使用新定义，旧实例保留原定义及名称。
7. 只撤销模板贡献时，不能再选择其模板创建实例，已有实例仍按快照运行；如果同一个 bundle 同时撤销了实例所需的节点类型，则已有实例按节点规格暂停新执行并保留查看，依赖恢复并通过校验后按原有规则恢复。
8. 本期不从旧 DSH home 模板目录自动发现模板，也不在启动时向该目录复制内置模板。
9. 实现涉及工坊列表、选择器和名称展示时，按项目浏览器验收技能在隔离宿主中验收。
10. 分别验证宿主在重载前拒绝新配置，以及卸载后新一轮 YAML 读取或校验失败：前者不主动撤销尚在运行的旧贡献，后者不恢复旧有效定义；失败诊断与贡献状态一致，不新增模板回滚机制。
11. 模板先于所需节点可用时，工坊显示不可用模板及具体缺失类型；节点随后可用且校验通过时自动恢复。再使类型缺失或冲突，验证列表、详情与创建入口使用同一可用性结果；移除阻塞后恢复，不依赖补丁排列顺序。
12. 在干净的隔离 profile 中仅添加默认 bundle，即可使用三个内置节点和唯一的内置模板 mattpocock 中文版（`matt-pocock-wayfinder-workflow.zh`）；内置模板与独立第三方 bundle 使用相同加载和登记入口。
13. 模板因缺少节点而等待期间修改 YAML，再恢复节点：仍使用本次已读取的定义判定和创建实例；模板声明自身重载后才使用新文件内容，之前创建的实例快照不变。
14. 在两个 profile 中分别启用不同节点贡献，验证模板只消费所属 profile 的节点能力，同一 profile 的各工作区结果一致，不改变实例存储作用域。

## 验证边界

附属文件扩展的验收要求如下；已验证范围及剩余真实宿主项见[附属文件验收记录](../acceptance/template-attached-files.zh.md)，不能沿用原插件化验收的通过结论：

1. 本地模板包携带脚本及文档，仅 exports 暴露 YAML、不添加资源字段即可加载；Bash 同时读取包内文档并操作工作区文件。
2. 模板目录包含空格、引号等字符时，双引号引用保持完整路径；`DSH_TEMPLATE_DIR` 不参与 Django 输入引用校验，不依赖外部同名环境变量。
3. `exports` 映射至不同目录、声明目录名与模板 ID 不同时，变量指向实际解析 YAML 的父目录；嵌套、递归及逐项 Bash 引用同一来源。
4. 包内脚本 A 改成 B、文档修改后，不重载 YAML 也能在旧实例下一次实际执行时读到新文件；YAML command 修改后，旧实例仍执行快照原命令，已成功节点不重跑。
5. 真实持久化后重启，以及仅撤销模板登记后，原包仍在且节点可用时继续通过保存的目录执行。删除文件或移动包时显示 Bash 失败及实际错误，不重绑定至其他模板；不调用该文件的节点不因文件删除被整体阻断。
6. 缺少内部来源的扩展前实例继续运行普通工作区命令；变量保持未提供，不从宿主环境继承旧值或从模板 ID 猜测目录。
7. 固定 rc.1 真实宿主验证模板包位于工作区外时的读取，以及产物写入工作区；读取被拒绝时保留执行错误且不退回无沙箱执行。记录实际沙箱和系统权限，不把路径注入或模拟服务测试当作文件可访问的证明。
8. session_agent 保持原有提示词及会话行为，Bash 的输入转义、stdout 输出契约、失败重试和结果提交恢复保持原规则。

公开契约和产品行为已确认。实现采用 Studio 的 profile 模板登记、独立通用加载插件和已有节点公共能力；页面与创建入口均查询登记结果。

- 自动化以现有 Cordis 装配、HTTP 与真实临时存储、页面交互边界验证公开行为，包括配置拒绝、声明生命周期、节点冲突/恢复及两个 profile 的隔离。
- 固定 rc.1 的隔离宿主与真实浏览器验证默认 bundle、纯配置第三方模板、两个工作区、诊断、撤销与重载、实例快照和依赖恢复。
- 自动化与真实浏览器的覆盖分别记录；未执行项目及第三步联合验收不会写成已通过。
