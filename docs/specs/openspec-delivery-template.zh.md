# OpenSpec 需求交付内置模板

## 范围与行为

- 默认 bundle 通过通用加载器提供中文模板 `openspec-delivery.zh`，展示名称为“OpenSpec 需求交付工作流”；与现有 `matt-pocock-wayfinder-workflow.zh` 并列，不需要额外模板插件。
- 顺序为需求表单 → AI 起名 → 名称结果表单 → propose → apply → archive。入口表单产生原始 `request`；起名会话只读分析并推荐名称，用户通过结果表单提交 `change_name`。
- 原始需求和名称直接传给 propose、apply、archive。session_agent 完成只提交 `{}`，不从回复自动提取名称，不透传输入；后续独立会话从磁盘读取实际规划产物与已澄清决策。
- propose 调用 `openspec-propose`，仅生成规划文档；实质歧义在当前会话询问并等待回答。apply 调用 `openspec-apply-change`，按实际规划实施并验证。archive 调用 `openspec-archive-change`，按技能完成状态与规格同步检查，以及必要的用户选择。
- 所有会话手动启动并由用户标记完成。缺失技能、无项目根、阻塞、失败或取消不能视为阶段成功，不自动进入下一阶段。名称提交后固定；改名需重新创建实例，不自动选择其他 change。
- 模板不安装 OpenSpec 或 dsh、不自动初始化项目，不改造现有节点能力，也不增加提案审批或归档确认表单。

## 验收场景

1. 默认 bundle 包含两个中文模板声明；两份定义通过 DAG 和实际节点配置校验，公共加载器可登记并创建实例。
2. 新实例仅出现需求入口；提交需求后才进入起名，起名完成后才出现名称表单。
3. 填写名称后 propose 收到名称及完整原始需求，保留中文、引号与换行。apply 等待 propose 完成，archive 等待 apply 完成，且各自收到相同的两个字段。
4. 各会话不会自动启动，模拟完成最后一个会话后 DAG 完成；会话模型业务成功需另行真实宿主验证。
