# 节点解释业务状态，studio 统一持久化

为避免新增节点时持续扩充 studio 的公共状态字段，每种节点自行定义需要持久化的可序列化业务状态，并决定提供给前端的内容；studio 只解释公共执行阶段、错误和完成结果，统一协调状态持久化，不解释会话关联、命令执行进展等节点业务字段。

纯前端临时状态不要求进入持久化契约。form 的未提交草稿只保留在当前页面，以服务端接受的正式提交结果为准，不建设服务端草稿保存或跨页面同步。

重启后的业务恢复由节点实现，恢复进展仍通过框架保存。节点不直接依赖 studio 的存储、工作流或 DAG 实现。该分工同时保留节点的业务独立性和工作流的持久化协调能力；行为与验收范围见[节点模块契约与表单节点规格](../specs/node-modules.zh.md)，具体状态接口与恢复调用时机按其约束落实，尚未实施到代码。

服务端以就绪、动作和恢复三类入口与节点协作。工作流判定依赖就绪，节点决定执行、等待与业务完成，并决定是否将启动和结束的操作权交给用户；节点也可以保留控制权。框架不把界面的打开和关闭统一解释为业务启动或结束，界面操作的业务含义由节点定义。不强制所有节点具备相同的开始或完成操作，节点报告完成结果后仍由工作流协调持久化与 DAG 推进。

成功完成与取消／中止必须区分：成功完成产生结果并交由工作流推进 DAG，取消／中止不视为成功完成，也不以成功结果推进下游。节点决定是否支持以及是否向用户开放这些操作，不要求所有节点都支持取消；本期 session_agent/bash 保持原有行为，不因契约可表达取消而新增取消功能。
