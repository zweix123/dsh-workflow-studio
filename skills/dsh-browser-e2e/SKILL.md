# dsh 浏览器端到端验收

在真实 dsh 宿主中验证用户可见行为。组件测试、接口测试和截图本身不能代替浏览器端到端验收。

## 1. 确定场景与检查环境

从本次需求、`docs/specs/` 中对应规格和必要时的 `docs/dag-syntax.zh.md` 提取可观察的验收场景，记录操作与预期。覆盖本次改动相关的正常路径、错误路径及规格要求的主题、语言和屏幕尺寸。

每轮开始都检查实际可执行文件的路径和版本，重装后也执行同样的检查：

- 用 `command -v` 和版本命令确认 `node`、`npm`、`dsh`、`pnpm` 在当前执行环境中可用。Node 须满足仓库 `package.json` 的 `engines`，dsh 必须是 `0.2.0-rc.1`；不要根据旧会话或旧安装路径认定工具仍可用。`dsh plugin` 转交 pnpm 执行，dsh 已安装不代表插件安装条件齐全。
- 缺少工具、版本不符或执行失败时，报告具体检查与第一条错误，阻断依赖该工具的步骤。不安装或升级 dsh CLI，不擅自修改全局工具、PATH 或 npm/pnpm 配置。
- 构建依赖缺失时，按仓库锁文件用 `npm ci --registry=https://registry.npmjs.org` 安装；保留依赖版本约束。然后在仓库根目录执行 `npm run build`，构建成功后再注册插件。

模型认证默认跳过。不读取、复制或展示用户日常的 token、API key、凭据文件、`.env` 或含密钥的配置，也不通过输出环境变量寻找凭据。需要真实模型调用且缺少认证的场景标为未验证，不索取 token。

## 2. 准备隔离环境与插件

默认新建临时 `DSH_HOME` 和独立临时验收工作区，不依赖用户日常 profile、插件登记、存储或旧验收数据。插件注册、宿主启动及 Web profile 帮助命令始终使用同一个 `DSH_HOME`；不要运行会初始化日常 profile 的裸 `dsh web --help`。

按当前场景决定是否沿用环境：

| 场景 | 环境处理 |
| --- | --- |
| 首次验收、上一轮已结束，或 dsh 已卸载重装 | 新建临时 home 和工作区，重新检查工具、构建并注册插件；不续用旧 profile 的依赖目录、登录链接或浏览器状态 |
| 同一轮补测，或规格要求宿主重启及持久化恢复 | 沿用本轮 home 和工作区；需要加载新构建时，停止本轮宿主后以原参数重启，再确认登录与页面状态 |
| Agent 中断后继续 | 先核对已有记录中的 home、工作区、端口、进程及已执行场景；确认仍属于本轮且可用才继续。无法确认或环境已丢失时新建环境，重跑受影响场景，不宣称自动续跑成功 |

在本轮工作记录中保留 home、工作区、端口、进程或执行会话标识及场景进度，供重入和清理使用；不保存含 token 的登录地址。仅停止和清理可确认由本轮创建的资源。

将 `E2E_DSH_HOME`、`E2E_REPO` 分别设为本轮临时 home 与仓库的绝对路径，注册默认装配入口：

```sh
DSH_HOME="$E2E_DSH_HOME" dsh plugin --profile web add "$E2E_REPO/packages/dsh-workflow-bundle" --registry=https://registry.npmjs.org
```

只添加 Studio 单包不会装配公共节点登记与内置节点。补装验收夹具也使用同一 home 和公共 npm 源。若报 `ERR_PNPM_UNEXPECTED_STORE`，从该临时 profile 的错误信息或依赖元数据核对其原 store 路径，向插件命令传入一致的 `--store-dir`；不改全局配置，不删除共享 store。无法确定时重新创建隔离环境；需要保留的恢复场景状态不能直接丢弃，应先报告受阻。

插件添加成功后再启动宿主。注册或安装失败时记录第一条错误及所属步骤，先解决工具、下载源或依赖问题，不进入浏览器阶段猜测故障。

## 3. 启动宿主与建立浏览器会话

在临时 home 写入 `e2e.patch.yml`，关闭模型认证引导，并使用网页内目录选择器，避免系统目录弹窗抢占焦点：

```yaml
- id: ui-settings-models
  config:
    credentialOnboarding: false
- id: directory-picker
  disabled: true
- insert:
    - id: e2e-directory-picker-browse
      name: '@deepseek-ai/dsh-host-directory-picker-browse'
    - id: e2e-ui-directory-picker-browse
      name: '@deepseek-ai/dsh-client-ui-directory-picker-browse'
```

选择未被占用且不同于默认 3080 的本地端口，设为 `E2E_PORT`；占用时换端口，不停止别人的进程。启动并保持本轮宿主运行：

```sh
DSH_HOME="$E2E_DSH_HOME" dsh --profile web --patch "$E2E_DSH_HOME/e2e.patch.yml" --host 127.0.0.1 --port "$E2E_PORT" --no-open
```

确认服务就绪。启动失败时先查日志，记录第一条错误并修复实际问题；本机沙箱拒绝监听时，申请该本地端口的运行权限，未获准则报告受阻。

在 Codex 内置浏览器（`iab`）新建可见标签页，使用本次宿主启动时输出的完整 Web 地址完成登录，展示在 Codex 面板中。地址可能带 `token` 参数，仅用于本轮正常访问认证，不写入验收记录或提交文件。新建或重启宿主后重新确认登录，不能假定旧 cookie 或旧链接有效。

未建立登录 cookie 时直接打开裸地址会返回 401，也可能被浏览器报告为 `ERR_BLOCKED_BY_CLIENT`。`credentialOnboarding: false` 只关闭模型凭据引导，不关闭 Web 访问认证。先核对本次完整启动地址与实际登录结果，再判断浏览器控制是否受阻；不能仅凭裸地址失败结束验收。如仍出现模型认证引导，点击跳过，不填写凭据。

通过网页内目录选择器的路径输入框选择本轮验收工作区；不调用系统目录选择器或控制用户桌面。必须实际看到工坊入口及页面内容，才能进入场景验收。进程存活或 HTTP 成功不代表客户端插件激活；若出现 `Failed to load plugins` 或 `waiting for service: workflowNodeViews`，按缺失服务核对 bundle 是否已正确装配。

## 4. 执行场景与定位失败

通过浏览器 UI 控制工具读取页面状态、点击、输入和截图，按场景检查最终状态、错误反馈及必要的持久化结果。画布中的可访问性点击失败时，重新观察页面，改用同一内置浏览器的语义 DOM 定位。

失败时保留可复现步骤、必要截图和相关日志，区分环境准备、宿主启动、Web 登录、客户端加载与业务行为。修复后重新验证失败场景及受影响场景。不得用 `curl`、直接 API 调用或 jsdom 结果冒充浏览器操作；接口调用只辅助定位。内置浏览器控制不可用时，报告 E2E 受阻及已完成的其他验证。

## 5. 汇报与清理

逐项汇报规格出处、操作与预期、实际结果及通过/失败/未验证状态，列出未执行原因。按项目验收文档约定保存必要证据；日志及记录去除登录 token，临时目录不能作为唯一的长期证据。

正常结束或决定终止本轮时，先保存必要证据，再停止本轮宿主并清理本轮临时 home 和工作区；保留用户需要查看的浏览器标签页。需要继续补测时保留环境并记清重入信息，待本轮结束后清理。异常中断后不能假定资源已自动回收，按第 2 步核对归属再继续或清理。
